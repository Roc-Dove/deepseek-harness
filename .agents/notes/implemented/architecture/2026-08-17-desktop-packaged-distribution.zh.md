# Agent Note: 自包含桌面发行

Status: implemented

[English](2026-08-17-desktop-packaged-distribution.md) | 中文

## 问题

[桌面源码壳](2026-08-16-desktop-source-shell.md)为开发者提供了一个承载已交付 Web 载体的原生窗口，但它从已经安装依赖并完成构建的源码仓库启动 pnpm。这不是用户下载后直接打开的产品。可发行的桌面应用必须携带一起验证过的确切后端、Web 资源、运行时依赖与平台原生模块，不能再读取构建机器的源码仓库，也不能要求用户安装 Node.js。

二进制发行增加了源码壳原本不负责的两道边界。第一，打包必须区分经过审查的应用默认值与机器本机状态：构建者的凭据、`DSH_HOME`、会话、补丁、源码路径与 Node 注入环境既不能进入安装版，也不能重定向安装版。第二，只能在构建机器上启动的产物还不适合公开下载。macOS 发行必须覆盖 Apple Silicon 与 Intel，并通过 Developer ID 签名和公证；Windows x64 必须签名。这些操作需要受保护凭据，绝不能暴露给来自 fork 的拉取请求。

桌面应用仍是本仓库的实现细节，而不是 npm 库。若把安装包耦合到 dsh npm 族，就会把操作系统产物、独立版本、签名仪式和 GitHub Release 混进一条用于发布 workspace package 的 registry 序列。

## 决策

`apps/desktop` 在同一个回环 Web 载体上提供两种明确启动模式。源码模式保留 `pnpm run desktop:dev`，从准备好的源码仓库启动 `pnpm dsh web --port 0`，并可读取按顺序排列的 `DSH_DESKTOP_PATCHES`。打包模式从应用专属工作区出发，用 Electron 可执行文件的 Node 模式启动内置 `lib/bin.js`，因此既不需要系统 Node 可执行文件，也不需要 pnpm。后端通过子进程 IPC 报告规范的 `127.0.0.1` URL；文本输出探测器保留为源码模式的兼容路径。

打包先构建仓库，再暂存桌面 manifest 和仅含生产依赖的部署闭包。后端与构建后的 Web 前端复制到应用 resources 下，Electron 应用代码留在应用 archive 内。原生依赖来自生成安装包的同一操作系统与架构；构建不会为另一目标重新构建或跨平台复制原生模块。发行与暂存输出只放在 `.artifacts/desktop/` 下；安装后运行时验证会驱动打包后的 CLI 与回环 Web 启动，而不是从源码仓库解析文件。

私有桌面 manifest 被刻意用作只描述依赖的 `pnpm deploy` 根。它的生产依赖描述组装后端所需的 provider 与非可选 peer，即使 Electron 壳不会直接 import 它们。桌面 workspace 专属的 Knip 例外记录这种 manifest 级使用；暂存与产物验证仍会遍历部署后的运行图，并拒绝缺失依赖。

打包资源不可变，因此打包模式不会挂载面向源码的实时补丁/HMR watcher。经过审查的默认值与应用专属配置仍会在启动时完成组合；依赖 watcher 的文件变更会在下次启动时生效。源码模式继续保留实时监听约定。

打包版状态全新且归应用所有。Electron 用户数据目录里包含隔离的 `DSH_HOME`，以及作为后端当前工作目录的工作区。安装包绝不包含构建机器已有的用户数据、凭据、会话、本机补丁文件或源码路径。spawn 前，打包模式会移除 `DSH_REPO_ROOT`、`DSH_DESKTOP_PATCHES`、`NODE_OPTIONS` 和 `NODE_PATH`，再设置自己的 `DSH_HOME` 与部署标记。安装版没有 `--patch` 入口。因此 Vision Bridge 与经过审查的仓库默认值一样保持禁用，直到用户配置兼容的图片输入路由，并通过产品配置显式启用。

源码壳决策中的窗口与进程所有权规则保持不变。renderer 导航使用窄化的 HTTP(S) 策略。桌面进程拥有后端进程树，先通过 IPC 请求有序停止，再回退到有限等待的平台进程树结束。IPC 就绪消息只接受完全匹配的消息形状，以及 host 为 `127.0.0.1`、端口有效、不带凭据且位于根路径的 URL。

桌面发行使用独立的二进制发布通道：

| 目标 | 原生构建者 | 公开产物要求 |
|---|---|---|
| macOS arm64 | Apple Silicon macOS runner | Developer ID 签名与 Apple 公证 |
| macOS x64 | Intel macOS runner | Developer ID 签名与 Apple 公证 |
| Windows x64 | Windows x64 runner | Windows 代码签名 |

拉取请求与非发布型手动运行会在不使用发布 secrets 的情况下构建并验证三个目标。其未签名产物只保留为测试证据。`desktop-v<版本>` tag 必须等于私有桌面 package 版本，签名 job 才能进入受保护的 `desktop-release` environment。这些 job 使用平台凭据在原生环境重新构建、验证运行时，再把 DMG、ZIP 和安装程序连同逐目标构建清单与 `SHA256SUMS` 发布到同一个 GitHub Release。macOS 构建腿还要求打包应用通过有效的深度代码签名检查、Gatekeeper 评估与已装订公证票据验证；Windows 构建腿要求解包主可执行文件、安装程序，以及 packager 实际产出的任何独立卸载程序都具有有效 Authenticode 状态。checkout 凭据不持久化，workflow 默认只有仓库只读权限，只有最终 release job 获得 `contents: write`。签名 job 不会在拉取请求事件中运行，因此 fork 贡献无法触达签名或公证 secrets。

桌面 package 保持 `private: true`，并排除在 [dsh npm 发布序列](../process/2026-08-10-npm-release-sequences.md)之外。它的版本在独立版本线上有意变更，发行 tag 为 `desktop-v<版本>`。当前没有自动更新器；用户需要显式安装更新的签名发行版。

## 曾考虑的替代方案

**要求用户运行源码壳。** 拒绝，因为它要求源码仓库、Node.js、pnpm、已安装依赖、构建产物与终端知识。它保留为开发入口，而不是发行产品。

**把桌面 package 发布到 npm，并在首次启动时安装 Electron。** 拒绝，因为这仍把运行时获取与原生依赖选择交给用户机器，无法生成操作系统安装包，还会把桌面版本与 dsh package 族纠缠在一起。

**另行捆绑一份 Node 发行版。** 拒绝，因为 Electron 已经携带兼容的 Node 运行时。通过 Electron 可执行文件的 Node 模式启动内置 CLI，可以免去第二份运行时下载，同时保留既有 Host 与 Web 组装。

**从 macOS 交叉构建所有目标。** 拒绝，因为生产依赖闭包包含平台原生依赖，而且代码签名、公证和安装后运行时验证都是平台操作。每份产物都在其目标操作系统与架构上构建和验证。

**把开发者的 `DSH_HOME` 或补丁复制进镜像，让发行版看起来已经配置好。** 拒绝，因为这会分发会话、凭据、端点、本机路径与可变机器状态。可复现的产品是经过审查的代码与默认配置；用户数据从空白开始，并始终位于应用镜像之外。

**在第一版安装包中启用自动更新。** 拒绝，因为这会增加更新 feed、更新密钥所有权、回滚与降级策略，以及另一条特权网络路径。签名后的手动安装是更小的首发约定。

**把未签名 DMG 或可执行文件当作公开发行版。** 拒绝，因为构建成功不等于获得平台信任。未签名输出只用于 CI 排练与本机打包测试；公开交付必须经过签名，macOS 还必须公证。

## 结果

下载的安装包现在包含展示同一套 Web 组装所需的运行时；开发者从源码验证的就是这套组装。干净机器无需 Node.js、pnpm、源码仓库或终端即可安装启动。边界可复现：打包后验证使用产物内文件，开发者本机状态既不会复制进去，也不会由已安装后端继承。

发行负责人必须维护三条原生构建腿、一个受保护的 `desktop-release` environment、一份 Windows 签名身份，以及 Apple Developer ID 与公证 API 凭据。证书与 API 密钥是运维依赖，不是仓库内容。丢失或轮换它们会暂停公开发行，但不会阻止未签名的拉取请求排练。

安装包比源码壳更大，因为 Electron、后端依赖闭包、原生模块与 Web 资源都会包含在内。不同平台和架构的产物可以不同，并且在同一次发行中不能互相覆盖。workflow 会记录校验和，因此下载后的字节可以独立核对。

安装版从仓库默认值和全新的应用专属数据目录开始，其中包括禁用的 Vision Bridge。现有源码开发补丁不会随之迁移；用户必须有意迁移或重新配置产品状态。自动更新保持缺席，直到另一个决策明确更新签名、feed 所有权、回滚与兼容策略。
