# Agent Note: MCP 图片结果使用持久化附件投影

Status: implemented

[English](2026-08-16-mcp-image-result-attachment-projection.md) | 中文

## 问题

MCP 工具可以返回有序图片内容块，但最初的 [MCP 客户端决策](2026-07-07-mcp-client-plugin.md)会把每张图片转换成文本占位符，因为 harness 当时没有生产可用的图片路径。附件服务和支持图片的模型路由现已存在，因此即使当前路由能够消费图片，无条件丢弃仍会损失有用的截图和生成图片。

MCP 服务器属于外部输入。它声明的媒体类型、base64 字节、图片数量、总大小、附件形状字段和文本值不得绕过本地内容策略；当存储尚未生成持久引用就失败时，结果也不得声称图片已到达模型。本说明仅部分取代旧说明中的结果映射决策；MCP 包、传输、命名、发现和生命周期决策仍由原说明负责。

## 决策

### 准入与持久化存储

`dsh-mcp-client` 通过 `ctx.get()` 读取 `ctx.attachments`，并把 `@deepseek-ai/dsh-attachment` 声明为可选 peer，且不做运行时导入。缺少该服务时，原始 MCP 图片保留在执行局部值中，并渲染为文本占位符。

执行器会在图片准入前清理每个外部内容块。MCP 提供的 `attachment` 属性会被剥离并记录警告，且不会读取或解析其声称的 ID；形状有效的引用不能证明本地存储拥有它。如果同一块携带 base64 字节，这些字节会重新进入普通准入，只有本次调用成功执行 `saveImage()` 后返回的引用才受信任。非字符串 `text` 字段会在发布规范值前被移除并记录警告；富媒体投影和折叠投影还会各自要求字符串，否则发出 `[text: invalid content discarded]`。

执行器从最新 request header 解析调用路由，缺失时回退到 agent 配置的提供方和模型，然后要求 `ctx.llm.resolveModelInfo()` 报告支持 `image` 输入。路由缺失、仅支持文本或无法解析时，所有 MCP 图片都保持为占位符，且不会写入附件。

对于支持图片的路由，准入保留 MCP 内容顺序，并执行附件服务接受的媒体类型、`maxImagesPerMessage`、`maxImageBytes` 和 `maxMessageImageBytes`。编码大小检查在分配解码字节前执行。只有成功存储的图片才占用数量和总字节账本，因此无效或被拒绝的块不会阻止后续可准入块使用剩余预算。`saveImage()` 继续权威校验字节格式、声明类型和解码后的像素数。

### 规范值与模型投影

每张通过准入的图片都会在工具结果可提交前完成持久化保存。其原始 MCP `{ type: "image", data, mimeType }` 条目会在执行局部规范值中替换为 `{ type: "image", attachment }`；未变化的文本与其他 MCP 块以及 `structuredContent` 保留其协议顺序和值。Native 渲染会在同一位置发出由附件支持的 `ImageBlock`。嵌套 Code Mode 分派还会延迟一条包含有序富媒体投影、来源为该插件的 user 消息，因为嵌套规范值本身不会进入模型历史。

不受支持的媒体类型、配置的数量或字节超限，以及稳定的附件校验失败只影响对应图片块：经过清理的原始块保留在规范值中，模型渲染发出既有的 `[image: …, content discarded]` 占位符，插件记录不含图片字节的警告。模型路由查找失败也会先记录日志，再使用占位符。附件基础设施失败或未知存储错误会重新抛出，因此 `ToolRuntime` 会生成错误结果，而不会展示一项图片尚未提交却声称成功的调用。

## 曾考虑的替代方案

**继续丢弃所有 MCP 图片。** 否决，因为持久化图片存储和支持图片的路由已成为生产能力；无条件丢失会使 MCP 截图和图片生成工具无法在专门用于消费图片的路由上工作。

**把 MCP base64 内联到会话日志或模型请求。** 否决，因为日志持有持久引用而非大体积二进制载荷，适配器从附件存储解析已验证字节。内联字节会复制存储、膨胀历史，并绕过内容寻址的完整性校验。

**不检查调用路由就挂载图片。** 否决，因为下一次纯文本请求将无法序列化由此生成的历史。精确路由准入可避免工具结果使其自身会话变得不可路由。

**每逢图片不通过准入就让整个 MCP 工具调用失败。** 否决，因为一个远端块格式不受支持或超过配置上限时，同一成功结果中的文本和其他块仍有价值。逐块占位符保留这些信息。持久化存储失败仍会使整次调用失败，因为在没有承诺引用的情况下报告成功是不真实的。

**同时保留 MCP base64 与附件引用。** 否决，因为附件对象是已验证字节的持久来源。同时保留两份副本会向 Code Mode 暴露二进制载荷，并在准入后保留无界重复数据。

**引用形状有效时信任 MCP 提供的附件引用。** 否决，因为附件 ID 是本地能力，而不是可移植的 MCP 数据。只验证形状仍会让远端服务器绕过字节校验和配置限制，或探测本地存储中已经存在的对象。

## 测试

包级单元覆盖会固定图片数量、单图字节和总字节的精确上限与超限行为，以及混合块顺序、路由回退与拒绝、校验警告、存储错误的 fail-closed 行为、伪造的形状有效附件引用和对象文本值。一项无需密钥的 stdio 测试会调用真实 fixture MCP 服务器，证明有序多图片附件投影、规范值中的 base64 替换、嵌套延迟上下文和纯文本路由占位符。`mcp-image-result` ACP 快照会通过真实 Loader 组合启动已发布的 MCP 客户端，等待真实 MCP 发现路径完成 fixture 工具注册，再调用本地 stdio MCP 进程、持久化内容寻址的图片结果，并让第二次 replay 调用通过 `fromRequest` 解析该附件 ID；后续组装模型请求没有携带图片引用时，replay 会失败。refresh、replay 和快照 fixture 清单共同覆盖已提交 transcript。

## 后果

支持图片的路由会按服务器顺序收到 MCP 截图和生成图片，而仅支持文本或未配置附件的部署会保留此前明确的占位符行为。通过准入的 base64 会有意从规范结果中消失；调用方获得持久化附件元数据，并可通过附件服务解析字节。

准入按块执行，而不是对完整 MCP 结果做事务处理。前面的可准入图片可以挂载，后续块则可能变为占位符。如果前一个内容寻址保存成功后存储基础设施再失败，该调用会失败，而在附件垃圾回收实现前，前一个对象可能保持未引用状态；失败调用不会把它的引用发布到会话历史。

可选附件 peer 使纯文本安装仍可加载。部署挂载附件但选择非图片路由时，不会承担解码或存储成本。警告数量与被拒绝的图片块及剥离的入站声明成正比，而存储中断会通过普通工具错误路径暴露。
